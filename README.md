# 顺诚AI工作平台

美客多跨境电商（顺诚）内部工作平台。

现有板块：
- **选品中心** —— 家居大类（美客多官方一级大类 MLM1574）11 个二级分类 + 品类总览（含品类 × 店铺承接布局）
- **店铺矩阵** —— 18 家店的健康与风险对照 + 店铺规划（定位 / 品类 / 人群）
- **经营数据** —— 经营概览、数据体检、作业节奏、独立核算、产品核算
- **店铺合伙** —— 两位合伙人的损益结构与增量分红机制（金额待接入）
- **库存管理** —— 待接入

线上地址：https://lingkongwangyuan.github.io/shuncheng-platform/

**加一个家居二级分类页的完整步骤：**

1. 在 `scripts/16_build_homedata.py` 的 `META` 里加一条（分类名 → icon / slug / 简称）
2. 跑 `python scripts/16_build_homedata.py` 重新生成 `data/home.js`
3. 复制任一分类页（如 `cat-bath.html`），改 `data-page` 为新的 `slug`
4. 在 `data/categories.js` 的 `nav` → 选品中心 `children` 里加一行，`page` 指向新文件
5. 完成——导航高亮、面包屑、统计数字、国家切换全自动

**「其他」「家具安装」为什么没做页面：** 官方二级分类本来有 13 个，其中
`Instalaciones de Muebles`（家具安装）商品数为 0 的空分类，`Otros`（其他）是残差桶
（活跃率 0.5%、月销 198 件）。两者按老周要求暂不做页面，但数据仍在
`家居大类市场分析表_v1.xlsx` 里，随时可加回。
巴西表里同样有这两个桶，接巴西数据时已一并排除（只接两国一一对应的 11 个分类）。

**两站口径（2026-09-22 巴西站接入时定）：**
- 本币各自照录：墨西哥 MXN、巴西 BRL，**不互相折算、不当成同一量纲比较**
- 卡片/总表上的「年销(亿¥)」是**人民币口径**：墨西哥为折算值（源表只给 MXN 与美元，
  按源表声明的 1 USD ≈ 7.2 CNY 折算），巴西为源表已给值 —— 只有同一币种才可比
- 「客单价」两站源表都给了 ≈USD，统一取美元段，可直接比
- 「同期比」两站口径一致：累计同比 = 2026 年 1-8 月 ÷ 2025 年 1-8 月，
  由各国「大盘月度趋势图」逐月像素还原（墨西哥 37 个月、巴西 37 个月）
- 巴西站**没有 3 年趋势表**，其月度趋势卡是截图还原值，已在卡片标题与脚注标明
- 「家居大类大盘」卡已按站点拆成两个数据盒（🇲🇽 墨西哥 / 🇧🇷 巴西），两站用**同一组 8 项指标**
  逐格对照：总商品数 / 活跃商品数 / 活跃率 / 近30天总销量 / 近30天销售额 / 日均销量 /
  平均成交价 / **年销售规模（人民币）**。年销是两站唯一统一到人民币的口径：
  巴西为源表已给值（约 368.3 亿 BRL ≈ 513.4 亿¥），墨西哥为折算值（月销美元 × 7.2 × 12 = 191.8 亿¥），
  高亮格已标注「折算值 / 源表已给值」。
  数据由 `16_build_homedata.py` 生成到 `data/home.js` 的 `rootSites`，
  两站指标名在源表里不一致（墨西哥「近30天销售额」↔ 巴西「月销售额」），
  统一映射表在生成脚本的 `ROOT_BOX_DEFS`；渲染层 `marketSitesCard()` 按同一顺序逐格画，
  **新增站点只改数据层**，不动渲染层。

## 店铺矩阵（已接入真实数据）

数据来源：`数据底座/顺诚经营数据底座.xlsx` —— 3,827 条店铺日报，2026-07-01 ~ 09-19，18 家店 × 5 站点。

**更新数据只跑一条命令**（在项目根目录 `顺诚-美客多/` 下执行）：

```bash
python scripts/10_build_shopmatrix.py
```

脚本重新生成 `data/shops.js`，页面即刻生效。**不要手改 `data/shops.js`。**

### 三个计算口径（改动前请确认）

| 指标 | 算法 | 为什么这么算 |
|---|---|---|
| 色级风险率 | 红橙黄记录数 ÷ **有色级记录数** | 分母排除「未标注」，两名管理人才可比 |
| 未标注率 | 未标注记录数 ÷ 总记录数 | 单独成列，**不参与健康评分**；未标注 ≠ 健康 |
| 封停/30天 | 封停次数 ÷ 覆盖天数 × 30 | 各店记录天数差 5 倍（13 ~ 60 天），必须归一化 |

### 两个页面

| 页面 | 内容 |
|---|---|
| `shops.html` | 18 家店对照表，按「封停/30天」降序（最该管的排最前），支持按管理人筛选 |
| `shops-group.html` | 管理人对比（色级 vs 封停双轴）、站点风险分布、月度趋势、风险类型聚集、最近风险事件 |

### 已知数据问题（脚本只标注、不改数）

- **李彦辉出单口径存疑**：转化 7.23%，为所有店中位数的 6.9 倍，页面标「出单口径待核」
- **两名管理人截止日期不同**：石老师 09-18、李源 09-19，页面按各店实际日期展示
- **色级标注习惯不同**：李源 100% 标注，石老师 32% 未标注 —— 看风险率时务必同时看未标注率

## 经营数据（已接入真实数据）

同一份数据底座（3,827 条日报），换一个视角：**不看风险，看产出与记录习惯。**

**更新数据只跑一条命令**（项目根目录下）：

```bash
python scripts/11_build_opsdata.py
```

重新生成 `data/ops.js`。**不要手改。**

### 三个页面的分工

| 页面 | 回答什么问题 |
|---|---|
| `ops.html` 经营概览 | 在架规模多大、流量怎么分布、出单转化如何 |
| `ops-quality.html` 数据体检 | **哪些数能信、哪些不能信**（这一页最重要） |
| `ops-rhythm.html` 作业节奏 | 谁在录入、录得齐不齐（不是看谁卖得好） |

### 本模块的四条口径（改动前请确认）

1. **在架规模 = 快照，不是累计**
   取每个（店铺 × 站点）最新一条有效的「总链接数」再求和。各店快照日期可能不同（李源 09-19、石老师 09-18）。
2. **「今日上架」按作业档位呈现，不当上架量**
   全表仅 19 种取值（100 / 50 / 200 / 150 …），是"按哪个档位作业"，不是真实上架条数。
3. **「总链接数」「总出单」不跨批次**
   数据分 6 个录入 sheet，每批次内部重新累计。跨批次相连会出现假性下跌，所以只做快照、不画趋势。
4. **缺失与异常只标注、不填补**
   李彦辉出单口径异常由脚本自动检出并标「出单口径待核」，原始数值不改。

### 三个已知数据缺口（页面已列出，等补）

| 缺什么 | 影响 |
|---|---|
| 真实上架条数 | 「日均上架」对不上实际 |
| 当日出单补全（9 月缺 62%） | 转化率只能覆盖已填记录 |
| 成本 / 售价 / 物流 / 广告费 | 利润分析、广告分析无法建立 |

补齐前两项，经营分析精度才能上一个台阶；补齐第三项，才能解锁利润与独立核算。

## 配色铁律（改样式必须遵守）

1. **同色系禁止**：背景与文字不得同色相（浅橙底绝不配橙字）
2. **浅亮底**（相对亮度 > 0.85）文字对比度须 ≥ 4.5:1
3. **彩色浅底配深色字，深色实底才配白字**

改动样式后必须跑门禁：

```bash
python _tools/check_contrast.py
# 退出码 0 才可交付
```

该脚本会先把 `assets/theme.css` 内联，再调用对比度自检。会**自动扫描根目录下所有页面**（`_` 开头的临时文件除外），新增页面无需改脚本。
